# TarnMedia

[English](README.md) · **Русский**

Небольшой и читаемый WebRTC SFU на Go поверх [Pion](https://github.com/pion/webrtc).
Он пересылает звук, камеру и демонстрацию экрана между участниками комнаты,
пускает их по JWT, которые выдаёт *ваше* приложение, и больше не делает ничего.

TarnMedia — медиа-бэкенд [TarnVeil](https://tarnveil.ru), небольшого приложения
для переписки и звонков, и вынесен из него. Здесь около 1500 строк Go, поэтому
прочитать всё целиком — реальный способ разобраться, как устроен SFU.

## Статус

**Экспериментальный.** Работает в проде на одном небольшом развёртывании
(комнаты до 25 участников), есть юнит-тесты, но:

- **нет simulcast и выбора слоёв SVC** — каждый подписчик получает единственное
  кодирование издателя, поэтому большая комната обходится по худшему каналу;
- **нет длительных нагрузочных испытаний** и опубликованных цифр по ёмкости;
- API не заморожен и может меняться между коммитами;
- мейнтейнер один, обязательств по поддержке нет. Что это значит для сообщений
  об уязвимостях — в [SECURITY.md](SECURITY.md).

Берите, чтобы разобраться, для прототипа или как отправную точку, которую вы
готовы сопровождать сами. Если сегодня нужен закалённый SFU с командой за
спиной — берите LiveKit или mediasoup.

## Что умеет

- сигналинг по WebSocket с аутентификацией и привязкой к комнате: `GET /v1/ws`;
- одна дорожка Opus плюс камера и экран на участника;
- пересылка стандартных кодеков, о которых договорились браузеры (Opus, VP8,
  H.264 и всё, что поддержали обе стороны), без перекодирования;
- trickle ICE, пересогласование, периодические запросы ключевых кадров, точная
  проверка `Origin` по списку;
- ограниченный диапазон UDP-портов и настраиваемый публичный IP;
- control API только на loopback и с аутентификацией — выгнать участника,
  закрыть комнату;
- отзыв токенов, лимиты на частоту сигналинга, keepalive для WebSocket,
  эндпоинты `/health`, `/ready` и метрики Prometheus на `/metrics`.

Сознательно **не** делает: запись, перекодирование, SIP, выбор слоёв simulcast,
хранение чего-либо.

## Быстрый старт

```bash
export TARNMEDIA_JWT_SECRET='случайный-секрет-не-короче-32-символов'
export TARNMEDIA_CONTROL_SECRET='другой-секрет-не-короче-32-символов'
go run ./cmd/tarnmedia
```

В Windows PowerShell:

```powershell
$env:TARNMEDIA_JWT_SECRET = 'случайный-секрет-не-короче-32-символов'
$env:TARNMEDIA_CONTROL_SECRET = 'другой-секрет-не-короче-32-символов'
go run ./cmd/tarnmedia
```

Публичный обработчик HTTP/WebSocket слушает `:8088`, медиа идёт по UDP
`50000-50100`, control API и `/metrics` — на `127.0.0.1:8089`. По умолчанию как
источники браузера принимаются только `http://localhost:5173` и
`http://127.0.0.1:5173` — любое реальное развёртывание обязано задать свои.

TarnMedia также читает `.env` и `../.env` из рабочего каталога; переменные
окружения приоритетнее. См. [`.env.example`](.env.example).

### Docker

```bash
docker build -t tarnmedia .
docker run --network host \
  -e TARNMEDIA_JWT_SECRET=... \
  -e TARNMEDIA_CONTROL_SECRET=... \
  -e TARNMEDIA_ALLOWED_ORIGINS=https://app.example \
  tarnmedia
```

`--network host` здесь не сокращение пути. WebRTC требует, чтобы контейнер видел
и анонсировал тот адрес, до которого участники реально достучатся; с bridge-сетью
придётся публиковать весь диапазон UDP и задавать `TARNMEDIA_PUBLIC_IP` публичным
адресом хоста — это медленнее и легко настроить неправильно так, что заметите не
сразу. Поддерживаемый путь — сеть хоста.

## Конфигурация

| Переменная | По умолчанию | Что это |
| --- | --- | --- |
| `TARNMEDIA_ADDR` | `:8088` | Публичный слушатель HTTP/WebSocket. |
| `TARNMEDIA_JWT_SECRET` | *(обязательна, ≥32 символов)* | Секрет HS256, общий с вашим приложением. |
| `TARNMEDIA_ISSUER` | `tarnveil-server` | Ожидаемый claim `iss`. Поставьте issuer своего приложения. |
| `TARNMEDIA_CONTROL_ADDR` | `127.0.0.1:8089` | Слушатель control API и метрик. Только loopback, иначе запуск падает. |
| `TARNMEDIA_CONTROL_SECRET` | *(обязательна, ≥32 символов)* | Bearer-секрет для control API и для исходящей проверки сессии. |
| `TARNMEDIA_AUTH_URL` | `http://127.0.0.1:3001/internal/tarnmedia/validate` | Ваш эндпоинт проверки сессии (см. ниже). Только HTTPS или HTTP на loopback. |
| `TARNMEDIA_ALLOWED_ORIGINS` | локальные dev-адреса | Точный список «схема+хост» через запятую. |
| `TARNMEDIA_PUBLIC_IP` | *(пусто)* | Адрес, который анонсировать в ICE-кандидатах за NAT. |
| `TARNMEDIA_UDP_MIN` / `TARNMEDIA_UDP_MAX` | `50000` / `50100` | Диапазон UDP-портов для медиа. |
| `TARNMEDIA_ICE_URLS` | *(пусто)* | Свои STUN/TURN через запятую. Сторонние серверы по умолчанию не используются. |
| `TARNMEDIA_ICE_USERNAME` / `TARNMEDIA_ICE_CREDENTIAL` | *(пусто)* | Учётные данные к ним. |
| `TARNMEDIA_MAX_PEERS_PER_ROOM` | `25` | Жёсткий потолок на комнату, 2–100. |

## Интеграция с вашим приложением

TarnMedia не ходит в вашу базу и ничего не знает про пользователей, друзей и
права. Кто в какую комнату может войти, решает ваше приложение — и выражает это
решение короткоживущим JWT.

### 1. Выдайте медиа-токен

Подпись HS256 ключом `TARNMEDIA_JWT_SECRET`. Обязательные claims:

```json
{
  "iss": "your-app",
  "aud": "tarnmedia",
  "sub": "user-42",
  "userId": "user-42",
  "room": "voice-general",
  "participantId": "user-42__laptop",
  "sessionVersion": 7,
  "username": "alice",
  "displayName": "Alice",
  "avatarUrl": "https://…",
  "issuedAtMs": 1767225600000,
  "iat": 1767225600,
  "exp": 1767225900
}
```

Что проверяется при разборе: `aud` строго равен `tarnmedia`; `iss` совпадает с
`TARNMEDIA_ISSUER`; `exp` обязателен; `sub` непустой и равен `userId`; `username`
непустой; `sessionVersion` ≥ 0; `room` и `participantId` длиной 1–180 символов
без управляющих символов. Принимается только HS256. Время жизни держите
коротким — минуты, не часы.

`participantId` идентифицирует одно *устройство*, поэтому один пользователь может
войти дважды с двух устройств. `sessionVersion` — счётчик отзыва, о нём ниже.

### 2. Поднимите эндпоинт проверки сессии

Подписанный JWT сам по себе нельзя отозвать до истечения, поэтому при каждой
аутентификации по WebSocket TarnMedia стучится обратно в ваше приложение:

```
POST $TARNMEDIA_AUTH_URL
Authorization: Bearer $TARNMEDIA_CONTROL_SECRET
Content-Type: application/json

{"userId": "user-42", "sessionVersion": 7}
```

Ответьте **`204 No Content`**, чтобы пустить участника. Любой другой статус
отклоняет соединение. Здесь вы проверяете, что пользователь ещё существует, не
забанен и его текущий `sessionVersion` совпадает с тем, что в токене — увеличьте
счётчик при смене пароля или выходе со всех устройств, и выданные медиа-токены
перестанут работать немедленно.

Вызов рассчитан на loopback или тот же датацентр; если он не удался, соединение
отклоняется (fails closed).

### 3. Сигналинг

Подключитесь к `GET /v1/ws` и отправьте аутентификацию **первым** сообщением,
чтобы токен не попал ни в URL, ни в лог доступа прокси:

```json
{"event":"authenticate","data":{"token":"<медиа-JWT>"}}
```

Каждый кадр — `{"event": "...", "data": {...}}`, где `data` это JSON-объект, а не
строка с JSON внутри.

Сервер → клиент: `authenticated`, `participants` (снимки состава), `tracks`
(привязка дорожек к MID), `offer`, `candidate`, `error`.
Клиент → сервер: `answer`, `candidate`, `state` (флаги микрофона, камеры, экрана).

Оффер делает TarnMedia: он присылает `offer` всякий раз, когда меняется набор
пересылаемых дорожек, и ждёт от вас `answer`.

### 4. Control API (по желанию)

`POST /v1/control` на loopback-слушателе, `Authorization: Bearer $TARNMEDIA_CONTROL_SECRET`,
тело `{"action": …}` — `closeRoom`, `evictUser` или `revokeUser` (обесценить уже
выданные токены до указанного момента). Отвечает `{"ok":true,"affectedPeers":N}`.
Через него кик или бан в вашем приложении дотягивается до идущего звонка. Никогда
не выставляйте этот слушатель наружу.

## Эксплуатация

- Диапазон UDP для медиа отдавайте напрямую. Проксируйте только обработчик
  HTTP/WebSocket — гнать медиа через обратный прокси значит потерять весь смысл.
- `/metrics` живёт на loopback-слушателе, а не на публичном. Собирайте локально.
- Прежде чем доверять развёртыванию, проверьте звонок между двумя физическими
  устройствами в разных сетях, включая запасной путь через TURN. Именно обход NAT
  ломается в реальном мире, и ни один юнит-тест этого не покрывает.
- Учётные данные TURN для браузеров генерирует ваше приложение, а не этот сервис.
